## Scope for this task

### 1. Per-model stake enforcement + concurrent-registration cap (#37)

**Background:** `DinValidatorStake.sol` already has `modelMinStakeBounds[modelId]` (a `{min, max}` struct, `onlyOwner`-settable via `setModelStakeBounds`) and `maxConcurrentRegistrationsPerStakeUnit` (`onlyOwner`-settable via `setMaxConcurrentRegistrationsPerStakeUnit`) — both landed in #65 as **inert storage**, explicitly flagged as follow-up in that PR's description and in [Umer's reply to you on this issue](https://github.com/InfiniteZeroFoundation/DevNet/issues/37#issuecomment-5077205841) (2026-07-25): *"`DINTaskCoordinator` doesn't need to know its own `modelId` or look anything up yet; wiring that lookup (and solving the 'task contract doesn't know its registry ID' problem) is explicit follow-up work."* This task is that follow-up.

**a) Per-model stake floor.** `registerDINaggregator` (`DINTaskCoordinator.sol:286`) and `registerDINAuditor` (`DINTaskAuditor.sol:607`) currently only check `dinvalidatorStakeContract.isValidatorActive(msg.sender)`. Add a stake-floor check reading `modelMinStakeBounds[modelId]`:
- Give each task contract a way to know its own `modelId` (an immutable set in the constructor is the simplest fix, since the model owner already knows the ID `DINModelRegistry.registerModel` returned before deploying the task contracts — check `foundry/script/` for where task contracts get deployed and thread it through there).
- **Open question to resolve in your PR description, not silently:** the design (`MECHANISM_DESIGN §3`) describes the model owner setting their own per-model requirement, bounded by DAO min/max — but the only setter that exists today, `setModelStakeBounds`, is `onlyOwner` on `DinValidatorStake` (i.e., DAO-set, not model-owner-set), and there's no separate "chosen value within bounds" storage slot. The simplest correct wiring is to treat `modelMinStakeBounds[modelId].min` directly as the effective per-model floor in the registration check (`getStake(msg.sender) >= max(minStake(), modelMinStakeBounds[modelId].min)`), leaving a model-owner-facing setter (bounded by `.min`/`.max`) as an explicit fast-follow rather than building it here. If you think it's small enough to include now, propose it — otherwise note the deferral explicitly.
- When `modelMinStakeBounds[modelId]` is unset (`min == 0 && max == 0`), behavior must be unchanged from today (no floor beyond `minStake()`) — this is the same "not yet configured" sentinel pattern #65 already uses elsewhere.

**b) Concurrent-registration cap.** This is harder because it's cross-contract: a validator's concurrent registrations span every model's `DINTaskCoordinator`/`DINTaskAuditor`, not just one. There's no shared counter today. Proposed approach — confirm or refine in your PR description:
- Add a per-validator counter on `DinValidatorStake` (e.g., `activeRegistrationCount[address]`), incremented/decremented by calls from task contracts.
- Reuse the existing slasher-authorization trust boundary (`onlySlasherContract`, wired via `DinCoordinator.setDINTaskCoordinatorAsSlasher`/`setDINTaskAuditorAsSlasher`) rather than inventing a new allowlist — a task contract already authorized as a slasher is also trusted to report its own registrations.
- Increment in `registerDINaggregator`/`registerDINAuditor`; decrement when that GI's participation for the validator concludes (`endGI`, or wherever the equivalent lifecycle end is for aggregators/auditors — check both contracts, they may need different hook points).
- Cap check: `activeRegistrationCount[msg.sender] < (getStake(msg.sender) / minStake()) * maxConcurrentRegistrationsPerStakeUnit` is the shape implied by the parameter's name and MECHANISM_DESIGN §3's example ("one 10-DIN stake cannot back 20 tasks") — confirm the exact formula in your PR description since this isn't specified to the bit anywhere.
- When `maxConcurrentRegistrationsPerStakeUnit == 0` (unset), behavior must be unchanged (no cap).

**Tests:** round-trip + bounds-validation tests already exist from #65 for the storage itself — add enforcement tests: a validator below the model floor cannot register; a validator at the concurrent-registration cap cannot register for a further GI; existing registration behavior is unchanged when either value is left at its zero/unset default.

### 2. Dispute-bond and reward-treasury forwarding (#38 partial, #43)

**Background:** Three `TODO(task_210726_5): forward to DinTreasury` stubs remain live in source, confirmed today:
- `DINTaskCoordinator.sol:131` — `treasuryAccrued` (dispute-bond forfeiture accumulator)
- `DINTaskCoordinator.sol:1067` — `resolveDispute`'s upheld-dispute bounty top-up
- `DINTaskCoordinator.sol:1079` — `resolveDispute`'s frivolous-dispute forfeiture
- `DINTaskAuditor.sol:58` — `treasuryAccrued` (reward-settlement treasury bps share)

`DinTreasury.sol` has existed since #51 (merged 2026-08-07) and the dispute bond's DIN denomination was confirmed by #133 (merged 2026-09-10) — nothing is blocking this except that nobody's wired it yet. This closes both #38's dispute-payout-stub item and all of #43's remaining scope, since they're the same code path.

**a) Frivolous-dispute forfeiture (`DINTaskCoordinator.sol:1079`) and `DINTaskAuditor`'s reward-settlement treasury share (`DINTaskAuditor.sol:58`) — straightforward, mirror the existing pattern.** `DinValidatorStake.slash()` already does exactly this split (`DinValidatorStake.sol:238-245`): `burnAmount = actualAmount / 2`, `IBurnableToken(DIN_TOKEN).burn(burnAmount)`, then `DIN_TOKEN.safeTransfer(slashTreasury, treasuryAmount)`. Both task contracts already hold the tokens in question (the bond, the reward pool's treasury share) directly — no cross-contract pull is needed, just burn+push using the same call shape. Keep `treasuryAccrued` as a running cumulative counter for observability (emit an event on each forward), but the actual tokens should move immediately rather than sit in the contract.

**b) Upheld-dispute bounty top-up (`DINTaskCoordinator.sol:1067`) — not a simple push, flag this explicitly.** Unlike (a), this needs `DinTreasury` to pay *out* to reward a correct disputer, and `DinTreasury.withdrawETH`/`withdrawERC20` are both `onlyOwner` (`DinTreasury.sol:43,55`) — a task contract can't call either. This is a real access-control gap, not a wiring oversight. Options to weigh (pick one, or propose another, and say why in the PR description):
  - Extend `DinTreasury` with an authorized-withdrawer role (mirroring the slasher-authorization pattern already used elsewhere) so registered task contracts can pull a bounty.
  - Fund the bounty from a different source entirely (e.g., a small carve-out from the GI reward pool, or the disputed party's own forfeited stake) rather than `DinTreasury`.
  - Keep bounty as an off-chain/manual DAO action for now and just make the on-chain state (`disputeBondClaimable` credit) correct — i.e., treat the bounty top-up as genuinely out of scope for this task and say so.
  This sub-item touches `DinTreasury.sol`'s access control, which is shared platform infrastructure — flag it for Umer's review regardless of which option you pick, before merging.

**Tests:** conservation checks (forfeited bond amount always reaches burn+treasury, never stranded or double-counted); confirm `SlashingInvariants.t.sol`-style fuzz coverage extends cleanly to the new forwarding calls; a test exercising the upheld-bounty path with whichever option (b) resolves to.

### 3. Network-fee floor completion (#78)

**Background:** `Developer/design/gas-simulation-network-fee.md` is complete except one line it flags itself: `commitAuditScore`'s gas cost (the commit half of commit-then-reveal, added by #63 after this doc's baseline) isn't priced, only `revealAuditScore` is. The recommended floor (`275,916 gas × gas_price_ETH`, auditor path) also isn't consumed anywhere in contracts/config yet.

- Extend `foundry/test/GasSimulation.t.sol` (see its existing `test_gas_s2_auditScore_*` tests, `GasSimulation.t.sol:307-350`) with a `commitAuditScore` measurement at the same LOW/MID/HIGH participation scale as the rest of the suite.
- Update `Developer/design/gas-simulation-network-fee.md`'s recommended floor to include the commit-half cost, and mark its "Open items" caveat resolved.
- Land the resulting number as an actual DAO-settable parameter (a `networkFee`/`feeFloor`-style constant with a setter, matching the existing governable-parameter pattern from `MIN_STAKE`/`UNBONDING_PERIOD` in #65) somewhere it's actually read — confirm with Umer where that consumption point should be if it isn't obvious from the existing fee-router/model-registration flow.

**Tests:** new gas-measurement test passes and reports a number in the PR description; if a setter is added, a round-trip test for it (matching the `setMinStake`/`setUnbondingPeriod` test shape).

## 1. `dincli/sdk/session.py` — `DinSession` + `SignerProvider` (§2)

Per proposal §2 (already approved):

```python
# dincli/sdk/session.py
class DinSession:
    """Lazily resolves network, web3, account, config. No printing, no exit, no prompts."""
    def __init__(self, network: str | None = None, wallet: str | None = None,
                 signer: "SignerProvider | None" = None): ...

    @property
    def network(self) -> str: ...
    @property
    def w3(self) -> Web3: ...            # raises NetworkError if RPC unreachable

    @property
    def account(self) -> LocalAccount:
        """Resolve the signing account via the configured SignerProvider.
        NEVER calls getpass or any interactive prompt. Raises SignerUnavailable
        if no non-interactive credential is available, WalletError if the
        keystore is malformed or missing."""

    @property
    def config(self) -> dict: ...

@runtime_checkable
class SignerProvider(Protocol):
    def address(self) -> str: ...          # raises SignerUnavailable if none resolvable
    def can_decrypt(self) -> bool: ...      # True if usable key resolvable without further input
    def sign_transaction(self, tx: dict) -> SignedTransaction: ...
        # raises SignerUnavailable (no credential), WalletError (bad keystore/decrypt failure)
```

This replaces the runtime-resolution parts of `DinContext` (`cli/context.py`) minus console/exit/prompting — read `DinContext` end-to-end first to confirm exactly which resolution logic (network, `w3`, account, config) moves here vs. what's already SDK-side (`sdk/web3.py::get_w3`, `sdk/config.py`).

**Two adapters, not implemented in the SDK itself:**
- **CLI adapter** (lives in `cli/`, wraps `SignerProvider`) — wraps the existing keystore flow in `cli/utils.py::load_account`; it *is* allowed to prompt via `getpass` (that's the interactive boundary), then hands the resolved signer into `DinSession`.
- **Daemon adapter** (lives in `dincli/dind/`) — backed by a configured password source, must never prompt; any missing credential raises `SignerUnavailable`, which `dind` turns into a job error rather than a hang.

**Doc/design gap to close as part of this work** (from Umer's §2 review on issue #20, not yet reflected in the proposal doc): `dind start` prompts interactively for wallet/password *once* at process start, and the resolved signer stays in memory for that daemon's lifetime. Config can be added/changed later while the daemon is running, but only through a separate `dind config` command (interactive there is fine, same pattern as `dincli system connect-wallet`) plus a non-interactive `dind load config` trigger that just points the running daemon at already-resolved state — the daemon process itself never blocks on stdin mid-run. Document the daemon `SignerProvider` adapter against *that* session-held, interactively-bootstrapped state, not a raw env-var lookup, in whatever module/docstring ends up describing the adapter. You don't have to build `dind config`/`dind load config` this task (scope boundary #5) — just make sure the adapter's contract and docstring don't imply raw env-var-only resolution, since that's the gap Umer flagged.

## 3. `dincli/sdk/tx.py` — `send()` keystone (§5b)

```python
# dincli/sdk/tx.py
@dataclass
class TxReceiptInfo:
    tx_hash: str                   # 0x hex
    status: int                    # 1 success, 0 revert
    block_number: int
    gas_used: int
    nonce: int
    contract_address: str | None   # set for deployment txs (deploy flows read this)
    logs: list[dict]               # raw, JSON-serializable log entries
    _raw: "TxReceipt" = field(repr=False, metadata={"json": "omit"})
        # web3 AttributeDict receipt, kept for in-SDK event decoding; NOT serialized

def send(session: DinSession, contract_function, *, tx_params: dict | None = None,
         on_event: Callable[[str, dict], None] | None = None) -> TxReceiptInfo:
    """Estimate -> build -> sign -> send -> wait. Returns receipt info.
    Raises TransactionError with subcode tx_estimation_failed | tx_reverted | tx_timeout |
    tx_nonce_conflict | tx_replacement_underpriced | receipt_missing (sdk/errors.py)."""

def decode_events(receipt: TxReceiptInfo, contract_event) -> list[dict]:
    """Decode a specific event from a receipt, e.g. registry.events.ModelRegistrationRequested().
    Wraps web3's process_receipt so a future operations layer can build typed results
    without exposing raw web3 objects to consumers."""
```

Replaces `cli/utils.py::build_and_send_tx` — that function becomes a thin wrapper calling `send()` and mapping `TransactionError` to today's `console.print` + `typer.Exit(1)` behavior (scope boundary #2: identical CLI exit codes/output).

Retry-safety shape (§10, already resolved): on failure, `TransactionError.details` must carry `tx_hash` **if broadcast**, `nonce` if known, and a `broadcast: bool` flag distinguishing pre-broadcast (safe to rebuild) from post-broadcast (must confirm the existing tx, don't resend) failures. On success, `TxReceiptInfo` carries `tx_hash`/`nonce`/`status` — that's the full retry-decision surface a future daemon job-retry policy needs.

### Four open design questions from Umer's §5b review — resolve these as you build, not upfront in a separate design doc:

1. **Nonce management ([`BL-1`](../BACK_LOG.md), weigh this one heaviest).** `context.py::get_tx_params()` currently calls `get_transaction_count(address)` with no block param (defaults to `"latest"`, confirmed-only) — two transactions fired back-to-back before the first confirms collide on the same nonce today. Decide and document: does `send()` itself prevent this for concurrent submission (e.g. track an in-process nonce counter, or use `"pending"` block param), or is that a layer above `send()`'s responsibility? Whichever you pick, fix the live gap in `get_tx_params()`'s nonce fetch as part of this task — don't leave it as a documented-but-unfixed known issue.
2. **`on_event` callback vocabulary.** The proposal only shows `"submitted"` as an example event name. Define the full set `send()` actually emits (e.g. `submitted`, `confirmed`, `estimation_failed`, `reverted` — your call on exact names) and document it in the `send()` docstring so CLI and daemon consumers both know what to listen for.
3. **Timeout/polling parameterization.** `send()`'s signature above has no timeout/poll-interval params, but CLI (interactive, human waiting) and daemon (background job, different patience) likely want different wait behavior. Decide whether to add explicit params (e.g. `timeout_s`, `poll_interval_s`) with sensible defaults, or handle this a different way — document the choice.
4. **Replacement transactions.** `tx_replacement_underpriced` is a defined error subcode but the replacement flow itself isn't designed. Decide: is replacing a stuck tx a fresh `send()` call with a manually bumped nonce/gas (caller's responsibility), or does `tx.py` need its own `replace()` function? A fresh-`send()`-with-bumped-params approach is probably enough for this task — don't over-build a dedicated replacement flow unless the four-question review implies otherwise once you're in the code.

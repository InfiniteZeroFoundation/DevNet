# Part B — Ungrindable batch-assignment seed (#156 H-2, both tiers) — PR 2

**Starts after task_16 PR 1 (Part A) merges.**

## Design: reuse task_16 Part A's future-block seed

task_16 Part A fixes the dispute-redo shuffle (BL-11) with a **future-block seed fixed in advance plus a permissionless lock**. Part B uses the same pattern for the two regular batch-creation calls. We end up with one randomness pattern across the protocol, and one sequencer-trust caveat.

- **Anchor at the preceding state transition**, which the owner can't aim because the seed block is still in the future:
  - T1/T2: `closeLMsubmissionsEvaluation` (`DINTaskCoordinator.sol:472`) sets `aggSeedBlock[GI] = block.number + seedDelay`
  - auditor batches: `closeLMsubmissions` (`:411`, the transition to `LMSclosed`) sets `auditSeedBlock[GI]` the same way
- **A permissionless `lock…Seed(GI)`** requires `block.number > seedBlock`. It stores `keccak256(abi.encodePacked(blockhash(seedBlock), GI, <domain tag>))`, and if more than 256 blocks have passed (`blockhash == 0`) it re-anchors. Mirror task_16 A3 exactly, and never store or use a zero-derived seed.
- **`autoCreateTier1AndTier2` and `createAuditorsBatches` revert if the seed isn't locked.** Otherwise they don't change.
- **Both shuffles take the locked seed**, domain-separated so the address and index shuffles don't correlate, e.g. `keccak256(seed, "AGG")` / `keccak256(seed, "IDX")`. Drop `block.timestamp` and `msg.sender` from `_shuffleUintArray` entirely.
- **Delay parameter:** reuse task_16's `disputeSeedDelay` if it fits, otherwise add one with the same setter + non-zero-guard pattern. Say which in the PR.
- **`DINTaskAuditor`'s shuffles:** give them the same seed-taking signature as task_16 A1's coordinator helper. Don't add a third shuffle variant.
- **NatSpec:** state the residual trust assumption (the OP Stack sequencer produces `blockhash`), exactly as task_16 A4 does. VRF stays the mainnet follow-up.

# Part C — Commit-reveal on T1/T2 submissions (#156 M-1, aggregation side) — PR 3

**Starts after task_16 PR 3 (Part C) merges.**

## Design

Mirror PR #63's auditor commit-reveal, with one hardening:

- **Bind the committer into the hash:** `commitHash = keccak256(abi.encode(cid, salt, msg.sender, GI, tier, batchId))`, not `keccak256(cid, salt)` as #156 proposes.
  - Without `msg.sender`, a lazy aggregator copies an honest peer's *commit hash*, waits for that peer's reveal, and reveals the same `(cid, salt)`. That is exactly the free-riding M-1 is meant to stop.
  - PR #63's auditor hash (`keccak256(abi.encodePacked(score, vote, salt))`, `DINTaskAuditor.sol:1127`) has this same weakness. **Don't fix it here.** Open a new issue for it (auditor-side M-1 residual) and link it in the PR.
- **Reveal-window states.** `T1AggregationStarted` becomes the commit window, then a new `T1AggregationRevealStarted` state, then `finalizeT1Aggregation`. Same for T2 with a new `T2AggregationRevealStarted`. The owner opens each reveal window, the same way the auditor-side reveal is opened.
  - **Enum placement: insert in lifecycle position**, not append. This is the 2026-08-27 precedent recorded in `DINShared.sol:25-34`.
  - This shifts every later ordinal, so you **must**:
    - update `dincli/cli/utils.py`'s `states`/`stateDescription` mirrors
    - update [`DINShared.md` §2.1](../../Documentation/technical/contracts/DINShared.md)
    - post the new ordinal table on PR #29 so the subgraph mapping (task_16 C5) gets regenerated. Robbert owns the subgraph; don't push to his branch.
  - Route every new transition through task_16's `_setGIstate`.
- **Votes count only on reveal.** `t1Votes`/`t2Votes` and `t1SubmissionCID`/`t2SubmissionCID` are written in reveal, not commit. `finalize*` counts only revealed submissions. The `T1AggregationSubmitted`/`T2AggregationSubmitted` events (task_16 C1) move to the reveal function, with signatures unchanged. Add `T1AggregationCommitted`/`T2AggregationCommitted` events only if the subgraph needs them; ask on #29.
- **Commit but no reveal = missed submission for S2.** Check that the S2 slash loop and the dispute/recomputation paths (`:912`, `:947`, `:1275`) read revealed state only, and that reward-weight accounting in `finalize*` (task_100926_11's `aggregatorWeight`) is unchanged for revealed aggregators.
- **Don't change dispute semantics.** Disputes open against the finalized CID exactly as today.

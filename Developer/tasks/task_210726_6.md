## 2. Auditing: commit-then-reveal, encrypted test data, resampling (Issue #40)

Three design decisions, all resolved in principle (Abraham, 2026-07-21) — your job is implementation:

### 2a. Commit-then-reveal for auditor score submission

Auditors currently call `setAuditScorenEligibility` (line 515) in plaintext in one transaction, letting a later auditor copy an earlier one's score. Implement two-phase submission: `commitAuditScore(gi, batchId, modelIndex, commitHash)` where `commitHash = keccak256(abi.encodePacked(score, vote, salt))`, then `revealAuditScore(gi, batchId, modelIndex, score, vote, salt)` validating against the stored hash before running the existing scoring/eligibility logic. Add a reveal-window mechanic — check `DINShared.sol`'s `GIstates` enum before adding a new state, since it's shared across both task contracts. Auditors who commit but never reveal must not silently corrupt quorum counting.

### 2b. Encrypted audit test-data distribution

Current flow (`assignAuditTestDataset`, line 421) assigns a single plaintext-shared `testDataCID`. Whitepaper §5.2.3b specifies per-validator key encryption with on-chain key mapping. Add `mapping(uint256 => mapping(uint256 => mapping(address => bytes))) public encryptedTestDataKey` (GI → batch → auditor → their encrypted key), populated when `assignAuditTestDataset` runs. No dincli/Python decryption change required — on-chain plumbing only.

### 2c. Test-set resampling strategy

Reserved pool (~40%), resampled half per round, full pool in the final round. Primarily an off-chain sampling-policy design (where the test dataset is assembled before its CID is pinned) — document the algorithm, wire it into an existing dataset-assembly script if one exists under `dincli/`/`cache_model_0/`, otherwise write it as a design doc under `Developer/design/` and flag implementation as follow-up.

### 2d. Aggregator auditing (S4 disputes) — spec only here

Referenced for completeness; built once in Part 4, don't duplicate.

## 3. Rewards: per-GI pool, role split, settlement, claim (Issue #41, core scope only)

### What's broken today

`DINTaskAuditor.totalDepositedRewards` (line 16) and `RewardDeposited` (line 102) are declared but never written or emitted anywhere in the codebase. `DINTaskCoordinator.endGI()` (line 783) does nothing but flip `GIstate` to `GIended` — there is no settlement, no claimable-balance crediting, no claim function. This is a green field, not a partial implementation.

### What to build

1. **Per-GI pool, not a running total.** Replace `totalDepositedRewards` with `mapping(uint256 => uint256) public giRewardPool` (keyed by GI number) — a single running total can't support the "funded per-GI, settled per-GI" model MECHANISM_DESIGN §5 describes.
2. **DIN-denominated deposit.** Add `IERC20 public dinToken` + `setDinToken(address)` (`onlyOwner`, deploy-time — mirror Robbert's `DINModelRegistry.setDinToken` pattern for consistency). Add `depositRewards(uint256 gi, uint256 amount) external` pulling DIN via `safeTransferFrom`, crediting `giRewardPool[gi]`, emitting `RewardDeposited`.
3. **Precondition on `_startGI`.** Wire `DINTaskCoordinator._startGI` (line 159) to check the auditor contract's `giRewardPool(_GI) > 0` (or a DAO-settable minimum) before allowing the GI to start — revert with a clear custom error if unfunded. Follow the existing cross-contract reference pattern between coordinator and auditor.
4. **DAO-settable role split, not hard-coded.** `struct RewardSplit { uint16 clientBps; uint16 auditorBps; uint16 aggregatorBps; uint16 treasuryBps; }` — mirror Robbert's bps-based `DinSplit`/`EthSplit` pattern for codebase consistency. Default to 6000/2000/1500/500 (the 60/20/15/5 proposal). Setter validates the sum equals 10000. These numbers are explicitly not final.
5. **Settlement at `endGI`.** Once `GIstate == AggregatorsSlashed`, compute and credit `mapping(address => uint256) public claimable`:
   - Clients: proportional to `finalAvgScore` among accepted (`approved == true`) submissions, scaled by `clientBps`
   - Auditors: equal share per completed assignment (correctness enforced by slashing, not reward weighting), scaled by `auditorBps`
   - Aggregators: per finalized T1/T2 batch, scaled by `aggregatorBps`
   - Treasury share: accrue in a local `treasuryAccrued` variable with a `// TODO(task_210726_5): forward to DinTreasury once merged` comment and a settable treasury address for later wiring — `DinTreasury` doesn't exist on `develop` yet, don't block on it.
   - Split computation must happen fully on-chain so payouts are independently verifiable.
6. **Pull-payment claim only.** `claimRewards() external nonReentrant` — transfers `claimable[msg.sender]`, zeroes first (checks-effects-interactions), reverts on zero balance. **No push-transfer loops in `endGI`** — this is exactly the class of unbounded-loop gas-DoS risk your own PR #22 findings warned about elsewhere in these contracts.
7. **Anti-gaming — reuse Parts 1-2, don't reimplement:** zero reward below `passScore` (already gated via `approved`), fold-in duplicate discounting naturally reduces a duplicate's `finalAvgScore` contribution (if it exists per 1a), median-bounded score inflation bounds the client-reward basis.

### Explicitly not in scope

Protocol-emission top-up, actual `DinTreasury` forwarding (stub only), final role-split percentages, aggregator reward scaling with batch size (note as a TODO if time runs short).

### 2. `dincli/sdk/serialize.py` — `to_envelope()` + shared encoder

Per proposal §3. This is genuinely new code (no existing `--json` call sites to preserve behavior against), so the correctness bar is the serialization rules table itself:

```python
# dincli/sdk/serialize.py
def to_envelope(data: "DataclassInstance | None", *, error: DinError | None = None,
                 network: str | None = None, chain_id: int | None = None,
                 correlation_id: str | None = None) -> dict:
    """Wrap a dataclass (or an error) in the {status, data, error, meta} envelope (proposal §3)."""
```

Encoder rules to implement and test explicitly (proposal §3's "Serialization rules"):
- Fields tagged `metadata={"json": "uint256_string"}` → decimal string, not a JSON number (precision safety for JS consumers).
- Fields tagged `metadata={"json": "omit"}` (e.g. `TxReceiptInfo._raw`, when that type eventually exists) → dropped entirely from the envelope, never partially serialized.
- Small integers (GI number, indices, plain enum-backed ints) stay JSON numbers — don't stringify indiscriminately.
- `bytes`/`HexBytes` → `0x`-prefixed hex string.
- Addresses → checksummed string (reuse `Web3.to_checksum_address` or equivalent, don't hand-roll).
- Enums → name string (not the int value) in `data`; the proposal allows including the int in `details` on the error path, not here.
- `Decimal` → string.

There's nothing in the SDK yet with a `uint256_string`-tagged field to serialize against — write the encoder against a small test-only dataclass fixture that exercises every rule above, plus one real one: wrap `dincli.sdk.state`'s GI-state enum in a trivial dataclass and confirm it serializes to its name string. Don't force an envelope onto `manifest.py`/`contracts.py` outputs this task — that's `operations/`'s job later, out of scope here (boundary #3).

### 5. `dincli/dind/capabilities.py` — hardware/local capability detection (P4-2.2, hardware-only)

Detect, stdlib-first (avoid adding a new dependency unless there's genuinely no stdlib path — flag it in the PR if you do):
- CPU count (`os.cpu_count()` — already used in `health.py:83`, reuse it) and, if easily available without a new dependency, CPU speed.
- Total/free RAM — no stdlib cross-platform API exists for this; either add `psutil` (flag the new dependency explicitly in the PR, it's the standard choice) or document that RAM detection is deferred pending that decision. Don't silently skip it without a note.
- Disk free under the resolved state dir — already computed in `health.py:66-73` (`shutil.disk_usage`); factor it into a shared helper both `capabilities.py` and `health.py` call, rather than duplicating the try/except.

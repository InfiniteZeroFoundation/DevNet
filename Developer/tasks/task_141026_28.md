## Background

`DINTaskCoordinator.resolveDispute` sets `disputes[gi][tierKind][batchId].resolved = true` with no path back. `openDispute` reverts with `TC_DisputeAlreadyResolved` if called on an already-resolved batch. The result is that each batch allows exactly **one dispute per GI lifetime**, whether upheld or rejected.

This is a reasonable design choice at the scaffold stage, but it was never recorded:
- No comment in `openDispute` or `resolveDispute` explains the one-shot constraint.
- `Developer/design/slashing-taxonomy.md` describes the dispute flow without noting the limit.

A future reviewer or implementer who assumes disputes can be reopened will either silently hit `TC_DisputeAlreadyResolved` or incorrectly treat the constraint as a bug to fix. This task adds the missing documentation.

**No behavior change. Documentation only.**

## Changes

### 1. DINTaskCoordinator.sol — openDispute

Add a one-line comment directly above the `resolved` check:

```solidity
// One dispute per batch per GI: once resolved (upheld or rejected), the batch cannot be re-disputed.
if (disputes[_GI][_tierKind][_batchId].resolved) revert TC_DisputeAlreadyResolved();
```

### 2. DINTaskCoordinator.sol — resolveDispute

Add a one-line comment where `resolved` is set to true:

```solidity
disputes[_GI][_tierKind][_batchId].resolved = true; // permanent — see openDispute comment above
```

### 3. Developer/design/slashing-taxonomy.md — dispute resolution section

In the section describing the S4 dispute flow (open → lock seed → resolve), add a note:

> **One dispute per batch:** once a dispute on a batch is resolved — upheld or rejected — `resolved` is set permanently. No further dispute can be opened for that batch in the same GI. If multi-dispute-per-batch is ever needed, `resolved` would need to become a counter or a re-openable state enum; open a separate issue for that decision.

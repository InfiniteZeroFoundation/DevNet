## BL-19 — `dind start` PID-file TOCTOU race (`feat/din-daemon`)

`start()` in `dincli/dind/main.py` does:

```python
existing_pid = read_pid(paths.pid_path)
if existing_pid is not None and is_process_running(existing_pid):
    ...
    raise typer.Exit(1)
...
write_pid(paths.pid_path)
```

with no lock tying the check to the write — `dincli/dind/process.py`'s `read_pid`/`write_pid` are plain file I/O, no `O_EXCL`, no `flock`. Two concurrent `dind start` invocations against the same `--state-dir` (systemd `Restart=on-failure` retry racing a manual restart, or a double-invoked deploy script) both pass the check and both start clean — the second silently orphans an unstoppable daemon doubling job-claim traffic against the same SQLite DB. Reproduced live during the 2026-09-10 review.

**Fix:** make the check-then-write atomic. The standard pattern is opening the PID file with `os.O_CREAT | os.O_EXCL` (fails atomically if the file already exists) instead of checking existence first — or an `fcntl.flock()`-held lock file that `start()` holds for its lifetime and `status`/`stop` can probe non-blockingly. Either is acceptable; pick whichever composes better with the existing `StateDirs`/PID-path structure. The current stale-PID cleanup path (`remove_pid` before writing, when the file exists but the PID inside is dead) still needs to keep working — don't regress that while fixing the race.

**Test:** a regression test that actually races two `start()` calls (threads or subprocesses against the same `--state-dir`) and asserts exactly one succeeds — not just a unit test of the lock primitive in isolation, since the bug was specifically about the race window.

## BL-20 — container healthcheck can't detect `degraded` (`feat/din-daemon`)

`HealthHandler.do_GET()` in `dincli/dind/health.py`:

```python
try:
    payload = self._build_payload()
    body = json.dumps(payload).encode("utf-8")
    self.send_response(200)
    ...
except Exception:
    ...
    self.send_error(500)
```

`send_response(200)` fires unconditionally as long as `_build_payload()` doesn't raise — but `_build_payload()` itself computes `status: "degraded"` (stale `last_tick`, event loop hung while the health thread still answers) and only puts it in the JSON body, never the status code. `docker-compose.yml`'s `curl -f http://127.0.0.1:8787/health` only fails on non-2xx, so a daemon whose event loop has silently hung passes the healthcheck forever — undercutting the "Docker auto-restarts an unhealthy daemon" claim in the container handoff docs.

**Fix:** map `status: "degraded"` to a non-2xx response code (503 is the conventional choice — "temporarily unhealthy") while keeping `status: "healthy"` at 200. Update `docker-compose.yml`'s healthcheck comment/docs if they currently claim more than crash-detection. Decide and document explicitly whether `degraded` should also trigger the container's restart policy (probably not — restart is for a genuinely stopped process, and `degraded` likely means "still ticking, just slow" — but that's your call to make and write down, not silently pick one way).

**Test:** a test that drives `_build_payload()`/`do_GET()` into the degraded branch (stale `last_tick` written into the state store) and asserts the HTTP status code, not just the JSON body.

## BL-21 — `dind` persists no logs to disk (`feat/din-daemon`)

`configure_logging()` in `dincli/dind/logging.py` attaches a plain `StreamHandler` (stderr) with `JsonFormatter` — nothing is written under `StateDirs`, despite it already holding `jobs.db`/`dind.pid`/`preferences.json`. Under systemd (journald) or a container log driver, the supervisor persists logs; run directly in a terminal — the documented, tested path — stderr is gone when the session closes, leaving nothing to `grep` for "why did my node skip a job three hours ago," which matters for the non-expert operators issue #21 is aimed at.

**Fix:** add a `RotatingFileHandler` (stdlib `logging.handlers`) writing under `StateDirs` (e.g. `<state_dir>/dind.log`), alongside the existing stderr handler — don't remove stderr, systemd/container users still want it there. Pick sane defaults (e.g. 10MB × 5 backups) and make them overridable via env var, following the same `DIN_DIND_*` env-var convention already used for `--state-dir`/health host/port. Keep `configure_logging()` idempotent (it already is for the stream handler — don't double-attach the file handler on repeated calls either).

**Test:** start the daemon (or call `configure_logging()` directly), log a message, assert it landed in the file under the given state dir.

## BL-22 — `NonceManager._instances` never evicted (`feat/din-sdk`)

`NonceManager` in `dincli/sdk/tx.py` keys its per-`(chain_id, address)` cache in a class-level `_instances` dict with no eviction — correct and irrelevant for the CLI (one invocation per process), but `dind` is long-lived, so this is unbounded process-wide state for its whole run. Already caused real test pollution during `task_300726_8`: reservations leaked between test classes until each cleared `NonceManager._instances` in `setup_method`.

**Fix:** doesn't need to be fancy — an LRU-style bound (e.g. a simple max-size dict with oldest-eviction) is enough given the realistic cardinality (one daemon manages a small, bounded number of accounts × networks, not an unbounded set). Document the bound and why it's safe. If you'd rather thread an explicit teardown/reset instead of a cap, that's fine too — just make sure it's real cleanup, not another place tests have to remember to reset manually (fix the root cause the existing test workaround is compensating for, don't just carry it forward).

**Test:** a test that exercises enough `(chain_id, address)` pairs to trigger the bound/eviction and asserts memory doesn't grow unboundedly — not just that the existing manual-reset test-pollution workaround still passes.

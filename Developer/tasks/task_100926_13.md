### 1. Partial-slash tiers for S1/S2, plus S5/S6 (#38)

**Background** ([MECHANISM_DESIGN §4](https://github.com/InfiniteZeroFoundation/DevNet/blob/develop/Developer/design/MECHANISM_DESIGN.md#4-slashing--auditors--aggregators-p3-41--42--43)):

| # | Condition | Role | Current state |
|---|---|---|---|
| S1 | Missed audit vote | Auditor | Flat `minStake()` slash, `AUD_NO_VOTE` — `DINTaskAuditor.sol:1268` |
| S2 | Missed T1/T2 submission | Aggregator | Flat `minStake()` slash — `DINTaskCoordinator.sol:829` (`slashAggregators`) |
| S3 | Score deviation from median | Auditor | **Already wired**, gated behind `s3SlashingEnabled` (default `false`) — `DINTaskAuditor.sol:151,1229-1279`. Not in scope here; enabling it is an operational decision pending empirical threshold data, not a code change. |
| S5 | Recidivism (≥r partial slashes within w GIs) | Both | Spec-only, no code |
| S6 | Registration without capacity (registers, never participates, across models) | Both | Spec-only, no code |

**a) S1/S2 → DAO-settable partial fraction.** Today's flat `minStake()` "fully unstakes a floor-staked validator for one missed vote," which MECHANISM_DESIGN §4 explicitly calls over-punishment for a liveness fault. Add a DAO-settable fraction (matching the `s3DeviationThreshold`/`setS3DeviationThreshold` pattern already in `DINTaskAuditor.sol` — a public settable var + setter + event), applied to both `slashAggregators` (`DINTaskCoordinator.sol`) and `slashAuditors`'s `AUD_NO_VOTE` branch (`DINTaskAuditor.sol`). The exact fraction (MECHANISM_DESIGN suggests 25-50% as an example, not a final number) is your call to propose in the PR description — this is explicitly still an open decision (§9 item 2), not something to treat as settled.

**b) S5 — recidivism counter.** Needs a per-validator count of partial slashes within a rolling window of `w` GIs, escalating to a full slash + jail on the `r`-th occurrence. Open design questions to resolve and note in your PR description:
- Where does the counter live? `DinValidatorStake.slash()` is the single choke point for every slash call today, but it doesn't currently distinguish partial from full severity — you'll likely need to extend `slash()`'s signature (or add a parallel bookkeeping call) so the counter only increments on partial slashes.
- What "within `w` GIs" means concretely — a rolling GI-index window needs each slash call to carry a GI number, which `DinValidatorStake.slash()` doesn't take today (it's called from task contracts that know their own GI but don't currently pass it through).
- Escalation: once the recidivism threshold is hit, does the *next* triggering call become a full slash automatically, or does it require a separate step? Prefer automatic if it fits cleanly, but call out the tradeoff.

**c) S6 — registration-without-capacity counter.** "Registers, never participates, across models" implies a cross-task-contract counter, same shape as task_100926_12 §1(b)'s concurrent-registration-cap counter. **Check whether task_100926_12 has merged before starting this** — if its `activeRegistrationCount`-style counter on `DinValidatorStake` exists, extend it (or add a sibling counter) to also track a "registered but didn't submit anything" flag per registration, rather than building a second independent tracking mechanism. If task_100926_12 hasn't merged yet, propose the shared shape now and note the eventual merge point in your PR description.

**Tests:** partial-slash-fraction round-trip + a fuzz test confirming the fraction is applied correctly at the boundary (matches `SlashingInvariants.t.sol`'s existing style); S5 escalation test (r-th partial slash within the window triggers full slash + jail); S6 counter test (registers-without-participating across ≥2 GIs triggers escalating partial slash, per the "partial, escalating" tier in the taxonomy table).

### 2. General-dispute recomputation verification for S4 (folded in from #40)

**Background:** #40 closed 2026-09-10 with one line folded into this issue: *"Aggregator auditing: T1/T2 outputs verifiable by recomputation; any validator may open an S4 dispute."* `DINTaskCoordinator.openDispute`/`resolveDispute` already exist as a scaffold (from #66) — bond custody, dispute window, fresh-subgroup reassignment excluding the accused (`_assignFreshSubgroup`) — but adjudication is `onlyOwner` (centralized human judgment call), not an on-chain recomputation check. This is distinct from PR #110's dispute mechanism, which is test-data-integrity-specific (`DINTaskAuditor.disputeTestData`/`resolveDispute`) and doesn't touch aggregation outputs at all.

**This needs a short design note before code** — "verifiable by recomputation" for T1/T2 aggregation isn't specified anywhere beyond that one sentence, and aggregation itself is deliberately off-chain (per the existing gas-simulation design doc's baseline: "aggregation logic is off-chain — only the final CID goes on-chain"). Concretely, propose an answer to: what does a validator submit to prove a T1/T2 CID is invalid, and what does the contract check on-chain to adjudicate it without re-running the aggregation itself (which it structurally can't, since the inputs and computation are off-chain)? A plausible shape: the fresh subgroup reassigned by `_assignFreshSubgroup` re-runs aggregation off-chain and submits a new CID; if it matches the disputed one, the dispute is frivolous (existing forfeiture path from task_100926_12 §2a applies); if it doesn't, the original is invalid (upheld path applies). Confirm or refine this with Umer before implementing — this is the one item in either task where the design isn't already settled by a prior decision.

**Tests:** once the mechanism is agreed, a dispute-and-recompute-mismatch test and a dispute-and-recompute-match (frivolous) test, following `EncryptedTestData.t.sol`'s three-stage structure as a model for how PR #110 organized a similar staged-reveal flow.

### 4. Emission contract (#42)

**Background:** MECHANISM_DESIGN §9 item 5 records geometric decay per epoch and a GI-lifecycle-tied inflation guard as a **resolved design decision**, but no corresponding contract exists in `foundry/src/` — today's reward pool (`depositRewards`, #64) is entirely externally funded, there's no protocol-emitted subsidy top-up at all.

**Sequence this after §3** — the emission contract's decay-rate/epoch-length numbers should be checked against §3's income-stability simulation rather than picked independently, since they're feeding the same validator-income model.

- New contract (or extension of an existing platform contract — propose which, following the existing Transparent Proxy pattern used by `DinTreasury`/`DinFairLaunchDistributor`): per-GI reward subsidy on a geometric decay schedule, tied to GI lifecycle (decays per completed GI, not wall-clock time — confirm this matches the "GI-lifecycle-tied inflation guard" phrasing in §9 item 5).
- Mints via `DinToken`/`DinCoordinator`'s existing mint path (check `mintCap`/`totalMinted`/`faucetRetired` from #60 — the emission contract's minting should respect the same cap machinery, not bypass it).
- Steady-state target: emission → 0 as protocol fees mature to fund the reward pool on their own (per this issue's own framing) — the decay schedule should make this explicit (a final epoch or an asymptotic tail, your call, state which and why).
- DAO-settable decay rate/epoch length, matching every other governable parameter in this codebase.

**Tests:** decay-schedule unit tests (emission amount at epoch N matches the geometric formula); an integration test funding a GI's reward pool partly from emission and partly from external `depositRewards`, confirming no double-counting; a mint-cap-respecting test (emission can't push `totalMinted` past `mintCap`, and is a no-op post-`retireFaucet`).

### Deep-dive: PR #131 vs PR #134 diffs (checked out at `/home/umerm/tempdir/DIN/PRs/PRreview_131` and `PRreview_134`)

Read both diffs against `develop` in full (not just the PR descriptions). Confirms the redundancy call above and surfaces one concrete, non-cosmetic finding worth carrying forward:

**PR #131's `aggregatorWeight`/`totalAggregatorWeight` accumulation is more correct than PR #134's `isRewardableAggregator` boolean, and PR #134's version loses funds.**

- `DINTaskCoordinator._collectFinalizedBatchAggregators` (untouched by PR #134 — confirmed via diff, only the docstring above it changed) is explicitly documented as building **"one entry per (aggregator, finalized batch) pair"** — *"an aggregator who completed both a T1 batch and the T2 batch appears twice, earning proportionally more weight"* (task_210726_6 §3's spec, restated verbatim in the function's own NatSpec). This is deliberate, documented, pre-existing behavior, not something #121 asked to change.
- PR #131 preserves this exactly: it increments `aggregatorWeight[gi][aggregator]++` and `totalAggregatorWeight[gi]++` once per (aggregator, finalized-batch) pair inside `finalizeT1Aggregation`/`finalizeT2Aggregation` — an aggregator active in both T1 and T2 ends up with weight 2, same as the pre-#124 `_settleAggregatorRewards`'s behavior via duplicate array entries.
- PR #134 instead does, in `settleRewards`: `count = rewardableAggregators.length` (still duplicate-counted, since `_collectFinalizedBatchAggregators` is unchanged), `aggregatorShare = aggregatorPool / count`, then `isRewardableAggregator[gi][addr] = true` for each entry — a boolean write, idempotent on the second occurrence. `claimReward(gi)` then pays each rewardable aggregator **exactly one `aggregatorShare`**, regardless of how many finalized batches they're credited for.
- **Concrete failure:** T1 finalizes with `[agg1, agg2, agg3]`, T2 finalizes with `[agg1]` (agg1 did both) → `rewardableAggregators = [agg1, agg2, agg3, agg1]`, `count = 4`, `aggregatorShare = aggregatorPool / 4`. agg1 should earn 2 units (correct, proportional design) but `claimReward` only ever adds one `aggregatorShare` for agg1 — the other 1/4 of `aggregatorPool` is never credited to anyone, anywhere. It isn't misrouted to the treasury either (treasury share is computed once at `settleRewards` time from the bps split, independent of this). It's simply **stranded in the contract, permanently unclaimable** — a real loss-of-funds bug, not just an underpayment.
- Neither PR #134's own tests nor PR #131's exercise an aggregator finalizing both a T1 and T2 batch in the same GI (both use the shared `_runFullHonestGI` fixture: one T1 batch, no T2), so this doesn't show up in either test suite as-is.

**Resolution — revised 2026-09-10:** rather than close PR #131 and file a fresh follow-up issue, keep PR #131 open and update it in place once #134 merges to `develop`:
1. Rebase PR #131's branch onto `develop` (post-#134-merge).
2. Adopt #134's shape/naming (`giTotalApprovedScore`, `giTotalAuditWeight`, `auditorGIWeight`, `GIRewardSnapshot`, `claimReward(gi)`) and drop PR #131's now-duplicate client/auditor accumulation.
3. Keep/port PR #131's `aggregatorWeight`/`totalAggregatorWeight` per-(aggregator, finalized-batch) counter into #134's `claimReward`, replacing `isRewardableAggregator` (bool) — pay `(aggregatorPool * aggregatorWeight[gi][addr]) / totalAggregatorWeight[gi]` instead of a flat per-address share.
4. Add a test with an aggregator finalizing both a T1 and the T2 batch in one GI to lock in the fix (neither PR currently covers this).

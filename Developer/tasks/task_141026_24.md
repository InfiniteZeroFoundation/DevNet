## Background

Nothing currently verifies that `foundry/deployments/<network>.json` (and the `din_info` snapshot written by `dincli system import-deployments`) still matches what is live on-chain. A stale deployments file after a failed or partial upgrade silently routes calls to the wrong implementation, and there is no quick way to detect it without reading raw storage slots by hand.

This task implements a **read-only drift check** that compares the recorded deployments against the live chain and prints `OK` / `DRIFT` per item.

---

## Preferred approach: `dincli system verify-deployment`

A new subcommand added to `dincli/cli/system.py`, following the pattern of the existing `import-deployments` command. It reads `foundry/deployments/<network>.json` (or the `din_info` config file), connects to the configured RPC, and checks the following for each recorded proxy:

### Check 1 — EIP-1967 implementation slot

Read `bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1)` from the proxy address and compare against the recorded implementation address.

### Check 2 — EIP-1967 admin slot

Read `bytes32(uint256(keccak256("eip1967.proxy.admin")) - 1)` from the proxy address and compare against the recorded `proxyAdmin*` address.

### Check 3 — Runtime code hash

Fetch `eth_getCode(implementation)` and compute its keccak256. Compare against `keccak256` of the `deployedBytecode` field in the corresponding `foundry/out/<Contract>.sol/<Contract>.json` artifact (immutables section masked to zero). Report `DRIFT` if the hashes differ.

### Check 4 — Owner / DIN-Representative

Call `owner()` on each ownable contract and compare against the recorded owner address.

### Check 5 — Wiring

Verify the key cross-contract links:
- `DinCoordinator.dinToken()` == recorded `dinToken` address
- `DinCoordinator.dinValidatorStake()` == recorded `dinValidatorStake` address
- `DinCoordinator.dinModelRegistry()` == recorded `dinModelRegistry` address
- Slasher authorizations on `DinValidatorStake`: each task-coordinator address listed in the deployments JSON is an authorized slasher.

### Output format

```
[OK]    DINTaskCoordinator proxy → implementation 0xabc...
[OK]    DINTaskCoordinator proxyAdmin 0xdef...
[DRIFT] DINTaskAuditor implementation: recorded 0x111... actual 0x222...
[OK]    DinCoordinator owner 0xghi...
[OK]    wiring: DinCoordinator.dinToken → 0xjkl...
```

Exits 0 if all checks pass, non-zero on any `DRIFT` or `ERROR`.

## Alternative: forge script

If the dincli approach is too heavy for the use case, a forge script `script/VerifyDeployment.s.sol` is acceptable. It should read the same deployments JSON via `vm.readFile` + `stdJson`, perform the same five check categories above, and output to stdout. Either approach closes the issue.

Whichever path is chosen, record the decision in a comment on #244.

## Notes

- This check is read-only. It must never send transactions or modify any state.
- It covers only what the deployments JSON records. A clean run does not prove nothing else was deployed or authorized outside that file. Say this in the command's help text.
- Do not attempt to auto-repair drift. Report and exit only.
